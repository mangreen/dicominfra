# ADR 0009：可替換性原則與假設登記

- 狀態：已接受（2026-11-24，經使用者要求）
- 範圍：整個專案；成案時要能輕易替換或修改任何東西

## 背景

這是 MVP／PoC 的展示。許多外部條件（推論平台、計費服務、身分、物件儲存、MCP 協定版本）尚未確定，
團隊同意先做簡單假設，但要求成案時任何一項都能輕易替換，不必重寫。

## 決定

1. **替換點（swap point）= Port 加 Adapter 加設定。**
   - Port 是使用方模組裡的 `typing.Protocol`，只描述我方需要的能力，不照搬任何一家外部服務的形狀。
   - Adapter 放在該模組的 `adapters/`，負責與外部格式互相轉換（Anti-Corruption）。
   - 由設定（`DICOMINFRA_<名稱>_ADAPTER`）在一個集中的組合根（composition root）選擇並建立；其他程式碼不得 import 具體 adapter。
2. **每個 Port 有共用的契約測試。** 測試在 `tests/ports/<port>/`，以 adapter 參數化；假 adapter 一定執行，真實 adapter 在提供連線設定時執行。
   換成真實服務時，通過同一套測試才算替換完成。
3. **假設一律登記在 [`docs/assumptions.md`](../assumptions.md)**：假設內容、PoC 的做法、替換點、驗證方式、需要誰確認、狀態。
   做出任何新假設時先登記；假設被確認或替換時更新狀態。PR 範本要求回答「是否新增或改變假設」。
4. **易變的規則做成設定或資料，不寫死在程式裡**：去識別化規則、配額上限、重試與退避參數、逾時、錯誤碼映射、事件類型到計費單位的對應。
   安全性與業務相關的數值是必填設定，不提供預設值（範例值只放在 `.env.example`，且標示僅限本機）。
5. **所有跨邊界的格式都帶版本**：推論契約、計費事件、MCP 工具 schema。schema 是單一事實來源。
6. **替換演練（M6）：** 挑一個替換點實際替換一次（例如把假計費服務換成另一種事件格式，或把 broker adapter 換掉），
   記錄變更的檔案與行數，作為「可以輕易替換」的證據。

## 誠實的限制：不抽象的部分

「任何東西都能替換」不是零成本，每個 Port 都要付出 adapter 與契約測試的成本。因此：

- **只對登記表上的替換點建立 Port。** 沒有登記的內部細節不抽象，避免為了抽象而抽象（符合 ADR 0007 的原則）。
- **刻意不抽象的技術基礎：** Python 與 FastAPI、PostgreSQL（含 RLS 租戶隔離與 outbox，見 ADR 0001、0002）、JSON Schema 作為契約格式。
  替換它們等於重寫。資料存取仍集中在各模組內，並使用 migration，把影響範圍限制在模組之內。
- 內部模組之間的替換靠模組邊界（公開介面），不靠到處加介面。

## 後果

- 開發成本較高：每個替換點要多寫 adapter 與契約測試。
- 假設變得可見、可追蹤，成案時能逐項確認，不會悄悄變成既成事實。
- 登記表需要持續維護，否則會失真；以 PR 範本與 AGENTS.md 的規則約束。
