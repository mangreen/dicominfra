# ADR 0004：Agent 獨立專案，透過 MCP 使用服務

- 狀態：方向已接受（2026-11-23）；下列細節為提議，待團隊決定
- 範圍：Agent 與醫療影像服務之間的邊界

## 背景

使用者除了 API 之外，也希望透過 Agent 取得服務。Agent 與服務的演進速度與風險不同，
且服務不應該信任 Agent。

## 決定

1. **方向（已確認）：** Agent 不內建於服務，是獨立專案，只透過 MCP 與服務互動。
2. **（提議）MCP server 為薄轉接層**，獨立進程，沒有資料庫權限，只呼叫公開的 REST API，因此 Agent 與一般客戶端走同一條授權與租戶隔離路徑。
3. **（提議）Token：** 依 MCP 授權規範，MCP server 只接受發給自己的 token，且不得把收到的 token 轉傳給上游 API；
   呼叫 API 時使用另一組憑證，並標明代表的使用者。
4. **（提議）寫入核准在服務端：** 「重送」這類改資料的動作，由 MCP 建立提案，使用者本人以自己的身分在服務端核准。
   核准不依賴 Agent 或 MCP 客戶端，因此 Agent 被誘導也無法替使用者核准。
5. **（提議）連線：** 使用者到 Agent 使用 SSE；Agent 到 MCP 使用 Streamable HTTP 的一般請求，回 JSON、無狀態；
   MCP 到 API 為短請求。長時間分析回傳任務編號，由 Agent 輪詢，不佔用連線。
6. **（提議）Agent loop 自行撰寫**，LLM 供應商以兩個 adapter 涵蓋（Anthropic 原生、OpenAI 相容），離線時降級為規則／狀態機模式。
7. 工具輸出一律視為不可信資料，只回傳已去識別化的欄位，並限制長度。

## 後果

- 多一跳呼叫與兩個專案的版本需要一起管理。
- 長連線與 LLM 串流的負載由 Agent 層承擔，醫療影像服務維持短請求。
- 殘餘風險：Agent 仍可能被誘導做「允許範圍內」的錯誤操作，因此寫入工具要少、可回復，並完整稽核。
- Agent 專案放在同一個 repo 的子目錄或獨立 repo，尚待決定。
