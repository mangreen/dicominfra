# ADR 0001：Modular Monolith 加獨立 worker 進程

- 狀態：已接受（2026-11-23）
- 範圍：PoC 後端整體架構與技術棧

## 背景

職缺描述的後端負責臨床資料、非同步影像流程、多租戶隔離與外部平台整合，團隊小、範圍大。
PoC 在雙核、16 GB 的開發機上開發，沒有 GCP 預算，需要先在本機完整跑通。

## 選項

1. **Modular Monolith（單一 codebase，API 與 worker 為不同進程）**
2. 微服務：獨立部署與擴展，但分散式成本（部署、追蹤、契約版本）對 PoC 不划算。
3. 單一進程同時跑 API 與背景工作：最簡單，但 CPU 密集的 DICOM 處理會拖垮 API。

## 決定

選項 1。技術棧：Python 3.12、FastAPI、PostgreSQL 16、RabbitMQ、uv、ruff、`mypy --strict`、pytest。
目錄以功能為單位組織（`identity`、`studies`、`deid`、`inference`、`results`、`usage`），模組之間只透過公開介面互相呼叫。
CPU 密集工作（pydicom 解析、去識別化）放進 worker 的執行緒或行程池，不阻塞 event loop。

## 後果

- 部署單位少，容易在本機以 Compose 重現。
- 模組邊界靠紀律維持而非部署邊界，需要靠 review 與依賴方向檢查守住。
- 若日後需要獨立擴展某個模組，可以沿著既有邊界拆出，成本較低。
