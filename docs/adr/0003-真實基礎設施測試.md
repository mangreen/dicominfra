# ADR 0003：以 Compose 與 CI 服務容器提供真實基礎設施，不使用 testcontainers

- 狀態：提議中（待確認）
- 範圍：整合測試如何取得真實的 Postgres 與 RabbitMQ

## 背景

團隊規範要求測試跑在真實的資料庫與 broker 上，不用 mock。開發機為 2014 年的雙核 MacBook Pro，
Docker Desktop 4.12（Compose v2.10）較舊；每個測試各自啟動容器的成本與穩定性都不理想。

## 選項

1. testcontainers：測試自行啟停容器，隔離最好，但需要 Docker socket，且啟動慢。
2. **由 Compose（本機）與 GitHub Actions 服務容器（CI）提供服務，測試只讀取連線環境變數。**
3. 在沙箱或本機直接安裝服務：環境差異大，難以重現。

## 決定

選項 2。`compose.yaml` 只使用 Compose v2.10 支援的基本功能。測試讀取 `TEST_DATABASE_URL`、`TEST_AMQP_URL`；
缺少時測試**失敗而非略過**，避免缺少真實服務被誤認為通過。
每個測試自己建立並清理獨立的資料表（或 schema），不依賴其他測試的狀態。

## 例外

不可控的外部服務（內部平台、LLM）使用替身：可注入故障的假平台、可腳本化的 fake LLM。
替身只能放在 `tests/` 或 `tools/`，不得進入正式映像。

## 後果

- 測試不會自行啟動服務，需要先 `make up`（或由 CI 提供）。
- 本機資源有限，重型整合測試以 CI 結果為準。
- 若日後需要測試隔離更強，可以改為 testcontainers，不影響測試內容。
