# ADR 0008：用量以本地帳本記錄，非同步送交計費服務

- 狀態：提議中（待確認；含需要平台團隊回答的問題）
- 範圍：本服務與內部計費服務的整合，以及計費服務故障時的行為

## 背景

職缺描述要求整合內部平台的用量計費，並且在平台不可用時產品仍能運作。
計費服務不歸我們管，可能逾時、回錯、重複收到事件，也可能長時間中斷。

## 選項

1. 在案件處理流程中同步呼叫計費服務：簡單，但計費服務一故障，案件就無法完成。
2. 完成後才呼叫，失敗就忽略：會漏帳。
3. **本地用量帳本加非同步送出**：帳本與案件狀態同交易寫入，之後由獨立進程送交計費服務。

## 決定

選項 3。

1. `usage_events` 帳本為 append-only：`id`（同時是送交計費的冪等鍵）、`tenant_id`、`study_id`、`event_type`、`quantity`、`unit`、`occurred_at`、`status`（待送出／已送出／已拒絕）、`attempts`、`next_attempt_at`、`last_error`。
   `(tenant_id, study_id, event_type)` 唯一，重複寫入只會被約束擋下。事件不含任何病患資訊。
2. 帳本與案件狀態在同一個交易寫入，因此不會有「完成了但沒記帳」或「記了帳但案件失敗」。
3. Billing reporter 以 `FOR UPDATE SKIP LOCKED` 取出到期的事件送出：
   - 成功或對方回 409（已記錄）：標記已送出。
   - 永久性 4xx：標記已拒絕並告警，不重試。
   - 逾時、5xx、連線失敗：指數退避加抖動，重新排程；**不設嘗試上限，也不丟棄**（用量不可遺失），改以事件年齡告警。
4. 斷路器：連續失敗達門檻就暫停呼叫一段冷卻期，之後以單筆探測，避免在對方故障時持續施壓。
5. 送出時帶原始的 `occurred_at`，讓延遲送達的事件仍落在正確的計費週期。
6. 定期對帳：比較帳本與計費服務的彙總，產出差異報告；帳本是我方稽核與爭議處理的依據。

## 待決策：計費服務同時負責配額或授權時

若計費服務也決定租戶能不能用，它故障時有兩種選擇：

- **fail-open（建議）：** 使用最近一次快取的配額，並設定「未送出用量」的上限，超過上限才暫停接受新案件。優點是符合「平台故障時產品仍可運作」；代價是有營收損失的風險，上限需由業務決定。
- **fail-closed：** 一律拒絕新案件。最安全，但計費服務故障就等於產品故障。

## 需要平台團隊回答

1. 計費事件的格式、單位與冪等語意：重複的事件 ID 回什麼？
2. 是否接受遲到的事件，計費週期怎麼認定？
3. 是否提供查詢或彙總 API 供對帳？
4. 是否同時負責配額檢查？故障時的預期行為？
5. 速率限制與批次送出的支援。

## 後果

- 計費服務故障不影響案件處理，但用量會延遲出現在計費系統。
- 帳本在長時間中斷下會成長，需要告警與維運手冊（M4 建立 runbook）。
- 測試（M4）：以假計費服務注入逾時、5xx、重複送達、409 與永久 4xx，驗證計費中斷時案件仍完成、恢復後不重複也不遺漏、斷路器與對帳行為。
